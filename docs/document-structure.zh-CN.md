# 第二大类：结构解析与结构感知切块

本次改动位于导入完整性与向量检索之间，保留标题、条款和表格记录的上下文。目标是让查询命中的片段仍能说明“属于哪一章、哪一条、哪个表和哪些列”。它提供改善召回与重排的基础，尚未测量实际业务数据的 Recall@K 或答案准确率。

## 具体改动

| 环节 | 当前行为 |
| --- | --- |
| DOCX | 使用项目已有依赖 Mammoth 先转换为 HTML，再保留为 Markdown；保留标题、段落、列表和表格，不再只提取纯文本 |
| 中文 DOCX 标题 | 除默认样式映射外，明确支持“标题 1”和“标题1”等 1—6 级样式名 |
| 本地 HTML | 在严格解码后转换为 Markdown；使用文档专用转换方式，保留文档开头、结尾和参考文献，不套用网站正文筛选 |
| PDF 与普通文本 | 识别文字中明确出现的中文篇／章／节、条款、编号和英文 Chapter／Section／Article；没有从空格猜测 PDF 表格 |
| Markdown | 支持 ATX／Setext 标题和表格；代码围栏内部的标题、条款及表格示例不被当作正文结构 |
| CSV 与 XLSX | CSV 按完整记录识别，包括双引号、引号转义和引号内换行；XLSX 正常文档导入生成的每个工作表标记为 CSV 表达 |
| 共享切块器 | 按章节、条款和表格边界组织片段；超长正文使用中英文句子标点及换行选择切点；重叠边界避免拆开补充平面汉字 |
| 向量数据库 | LanceDB、Chroma、Milvus、Pinecone、Qdrant、Astra、Weaviate、PGVector 均传递文档表达类型，使用同一共享切块逻辑 |

没有增加生产依赖或修改锁文件。DOCX 使用原本已声明的 `mammoth`，文档 HTML 转换复用现有 `turndown` 和表格规则。

## 结构如何进入检索

```mermaid
flowchart LR
  A[原始文档] --> B[保留标题与表格的文本表达]
  B --> C[章节、条款、段落、表格块]
  C --> D[带上下文的切块]
  D --> E[现有嵌入模型与向量库]
  E --> F[现有检索与 reranker]
```

结构块含类型、原文起止偏移、章节路径、条款路径，以及可识别表格的列名和记录。偏移为 JavaScript UTF-16 单元，指向传入解析器的文本表达；DOCX／HTML 转换后指向 Markdown，不是原始文件坐标。

结构块在切块时按需生成于内存，没有复制进每个向量记录，也没有新增数据库表或结构报告目录。文档增加标量 `documentFormat`；DOCX 另外记录 `structureParser: mammoth-markdown-v1`。

片段中的上下文以可读文本形式参与嵌入、检索、重排与回答，例如：

```text
section: 第一章 交通补贴
clause: 第二条

第二条 试用期员工不享受交通补贴。
```

相邻独立条款作为边界处理，尽量避免把适用对象、例外条件不同的条款混在一起。超长条款仍需拆分，拆分后的片段继续带有章节和条款路径。路径很长时，在预算内保留靠近当前内容的部分。

长表按行分组，正常大小的行保持完整，每组重复表头。临近表格、可识别为“表1 …”或“Table 1 …”的表题也会进入上下文。CSV 重复第一条记录作为上下文；这里只能确定它是首行，不能保证它一定是业务列名。

结构上下文、重复表头、现有文档元数据与嵌入前缀均计入结构片段的字符预算。文档元数据太长、预算中不足以留下正文空间时明确报错，避免超出长度后默默截断。不含可识别结构的文档仍沿用原递归切块流程，该流程原有的元数据附加长度行为保留。

结构信息当前进入片段文本，没有新增章节字段过滤、父子片段回溯、跨文档关系推理或精确页码／表格单元格引用。

## 可验证的变化

一个构造样例包含“第一章 员工福利”“表1 交通补贴标准”、两列表头，以及从岗位编号 000 到 099 的 100 行数据，切块大小 240、重叠 20，不附加文档元数据：

| 指标 | 原递归切块 | 结构感知切块 |
| --- | ---: | ---: |
| 全部片段 | 11 | 13 |
| 包含数据行的片段 | 10 | 12 |
| 数据片段中保留完整表头 | 1 | 12 |
| 数据片段中保留表题 | 0 | 12 |
| 所有原始数据行均保留 | 是 | 是 |

这是上下文完整性的验证，不是使用真实嵌入模型测得的召回率。结构保留会增加片段或重复上下文，索引空间、嵌入调用和检索候选分布也可能变化。

验证结果：25 组、302 项测试通过；改动的 22 个 JavaScript 文件通过独立静态检查；`git diff --check` 通过。测试覆盖：

- 实际生成的 DOCX，经真实 Mammoth 和 Markdown 转换器进入结构感知切块，包括中文标题样式。
- 条款嵌套、章节切换、原文偏移、表题、表格列名、CSV 多行记录、长条款和补充汉字。
- 真实 LanceDB 入库，确认送入嵌入器的文本和入库文本均包含表格上下文，且未写入嵌套结构对象。
- 上一类导入完整性、原递归切块行为和已有 reranker 的回归。

LanceDB 入库测试使用确定性的模拟嵌入向量；reranker 回归沿用既有测试，不代表本次对业务文档进行了模型准确率评测。当前机器的采集器依赖未整体安装，验证时将已声明的 Mammoth 1.6.0、Turndown 7.2.4、node-html-parser 6.1.13 装入独立临时目录，通过进程级 `NODE_PATH` 加载，没有改动项目依赖目录或锁文件。

## 已知边界

- PDF 的文字提取顺序、分栏与复杂版面没有在本类重建。原文提取时已丢失的行列关系，不能靠切块恢复。
- 扫描表格、同页文字与扫描图混合、公式和图片中的条款，仍需版面分析与更强 OCR。
- DOCX 中的合并单元格按原有 HTML 表格规则保留占位；不会自动填充合并值，或把多级表头推断为完整业务字段。检测到合并单元格会产生导入警告。嵌套表格仍可能被转为单元格内文本。
- DOCX 内嵌图片显示占位并发出未 OCR 警告；有可用文字时返回 `partial`，只有图片而没有可用文字时返回失败。
- CSV 首行可能是标题、说明或数据，不能自动保证正确识别业务表头。XLSX 的合并信息未从现有解析器恢复；直接附件的 `parseOnly` 多表合并路径仍沿用原文本表达。
- 单行、单个单元格或表头超过片段预算时仍需拆分；表头过大时保留原文切分，不能保证每个片段都有完整表头。此类表需要后续单元格／字段级表示。
- 自定义标题、无编号标题、OCR 错字和复杂自动编号只能保守识别，可能漏识别或误识别。
- 当前仍整份加载文档，不提供超大文件的流式解析与断点恢复。

## 生效、回退和后续

重启采集器和服务端后，新导入内容使用上述流程。本类未修改前端，无需为本类单独重建前端。

DOCX／HTML 应重新导入并重新向量化，才能补回先前被压平的结构。对已有保留结构标记的文本重新向量化时，要确保不复用旧向量缓存；仅查询现有索引不会触发重新切块。生产运行配置没有在本次修改，服务也未自动重启。

默认启用结构感知切块。如需回到原切块方式，可在服务端配置：

```dotenv
DOCUMENT_STRUCTURE_CHUNKING=false
```

这只控制切块策略，不撤销已经存储的 DOCX／HTML Markdown 表达；修改配置后仍需重新向量化并绕过旧缓存。内部调用可用 `new TextSplitter({ structureAware: false })` 覆盖默认值。

本类没有引入语义分词、Agent 切块、GraphRAG 或关系数据库。这里采用的是按显式结构组织资料的切块。后续应使用真实长中文文档及问题集比较召回与答案质量，再按主要缺陷推进复杂版面／表格解析、检索策略或精确数值查询。
